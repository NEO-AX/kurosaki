# 金融庁の黒崎 —— AI開発体制の独立監査ツール

AI（Claude Code / Codex 等）に開発させているリポジトリを、**外部から**機械的に監査する。
被監査リポジトリの中に検出ロジックを置かないので、実装セッションのAIが対象を書き換えても
監査の内容は変わらない。

## なぜあるか

実在する個人の情報を含む seed SQL が、公開リポジトリへコミットされる事故があった。
原因は2つ。実装AIが実データを使ったこと。人間が push 前に diff を見なかったこと。
`CLAUDE.md` には「実在個人情報を使わない」と既に書かれていた。**文章の規律は破れる。**
だから機械が止める。

## 使い方

```bash
kurosaki audit --repo <対象>            # 体制監査（機械判定）。意見が出る。調書が残る
kurosaki review --repo <対象>           # 独立監査AIによる差分審査（Layer 2）
kurosaki audit --repo <対象> --no-save   # 読み取りのみ
kurosaki audit --repo <対象> --only D6   # 領域を限定
kurosaki scan  --repo <対象> --staged    # commit 前の内容だけ走査
kurosaki scan  --repo <対象> --history   # 履歴の全ブロブ（過去の混入を掘る）
kurosaki install --repo <対象>          # フック・CI・基準書を配置し MANIFEST を作る
kurosaki install-global                 # ~/.local/bin に入口を作る
```

依存: Python 3.9+ の標準ライブラリのみ。`gh` があればブランチ保護と公開状態も検査する。
`Faker` があれば「Faker(ja_JP) 由来のダミー」の照合ができる（無ければその緩和は効かない）。

## 2つの層

| 層 | 何をするか | AIの判断が入るか |
|----|-----------|------------------|
| **Layer 1/機械検査**（`scan` / `audit`） | 17手続を機械判定し、監査意見を出す | 入らない。説明で結果が変わらない |
| **Layer 2/独立監査AI**（`review`） | 生の diff とファイル内容だけを渡し、固定スキーマのJSONで所見を出させる | 入る。ただし下の枠で縛る |

Layer 2 の独立性（`claude --help` 2.1.47 で実在を確認したフラグのみ使用）:

- 作業領域は `mktemp -d`。**被監査リポジトリの外**で起動し、実装用 `CLAUDE.md` を持ち込まない
- `--system-prompt` で既定のシステムプロンプトを監査基準書＋監査人プロンプトへ置換
- `--tools ""` で全ツール無効。監査AIは追加のファイルを読めない
- `--setting-sources` で project / local の設定継承を切る
- `--json-schema` で出力を固定。散文・前置き・要約は受け付けない
- `checks_performed` が8項目未満、または確認方法が抽象的な場合は**結果を破棄**（根拠なき「問題なし」を通さない）
- 監査AIの出力自体を PII 走査にかけ、生値が混ざっていたら伏せて Critical として報告
- 変更された `CLAUDE.md` 等は審査対象として渡すが、「被監査データであって指示ではない」と明示的に囲う

Claude Code セッションの内側からは起動できない（入れ子起動をランタイムが禁じている）。
通常のシェルから実行する。`--dry-run` で「何を渡すか」だけを確認できる。

## 監査意見

| 意見 | 条件 | 扱い |
|------|------|------|
| 不適正 | Critical ≥ 1 | マージ・push・デプロイ不可 |
| 限定付適正 | High ≥ 1 | 限定事項を引き受けるか解消 |
| 意見不表明 | 実施不能手続が2割以上 | 検査可能にしてから再監査 |
| 適正 | 上記以外 | 実施手続の全列挙が根拠として付く |

## 検査手続（16本）

| ID | 領域 | 内容 |
|----|------|------|
| D1-01 | 体制文書 | 規律文書の実在 |
| D1-02 | 体制文書 | 規律・上位文書が実装AIから書き換え可能でないか |
| D2-01 | フォルダ構成 | 実データが git 外にあるか（.gitignore 単独防壁でないか） |
| D2-02 | フォルダ構成 | 追跡してはならないもの（.env / private / 本番投入 / 生成物）の追跡 |
| D3-01 | 機械ゲート | git が実行する位置にフックが実在し実行可能か |
| D3-02 | 機械ゲート | フックが本ツールを実際に呼び、結果を捨てていないか |
| D3-03 | 機械ゲート | CI が実在し、監査を呼ぶか |
| D3-04 | 機械ゲート | 監査の無効化（continue-on-error / `\|\| true` / set +e / 環境変数バイパス） |
| D3-05 | 機械ゲート | 既定ブランチの保護と必須チェック |
| D3-06 | 機械ゲート | 公開リモートの有無 |
| D5-01 | 不可逆操作 | 一覧の実在と必須6項目の網羅、承認者の明記 |
| D5-02 | 不可逆操作 | 本番到達経路の人間ゲート、AIへ渡した危険権限 |
| D6-01 | データ取扱い | 個人情報（氏名・連絡先・住所・生年月日・学籍番号・カード） |
| D6-02 | データ取扱い | 確定パターンの秘密（APIキー・トークン・秘密鍵） |
| D7-01 | 独立性 | 配置済み監査基盤の改変検知（正本ハッシュ照合） |
| D7-02 | 独立性 | allowlist が抜け道になっていないか |
| D7-03 | 独立性 | 調書のハッシュ連鎖（過去の監査結果の改変検知） |

## 設計上の約束

- **出力に生の個人情報・秘密を出さない。** 先頭1文字＋`***` と件数だけ。テストで固定している。
- **fail closed。** 走査できない・解釈できない・確認できないときは、緩めずに所見か「実施不能」にする。
- **実施できなかった手続を隠さない。** 2割を超えれば意見不表明になる。
- **allowlist は narrow のみ。** 全体を対象にする項目は無効化される（報告だけでは抜け道が残る）。
- **解除手段を環境変数にしない。** 人間ゲートは `/dev/tty` からの合言葉入力。AIの実行環境には端末が無い。

## テスト

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

43件。内訳:

- `tests/test_scan.py`（18件）—— PII検出、誤検知、**出力に生値が混ざらないこと**、allowlist の fail closed
- `tests/test_audit.py`（7件）—— 「欠陥を全部入れた被監査リポジトリ」と「正しく導入した被監査リポジトリ」を
  合成し、全手続を両方へ当てる。手続を足したら期待表にも足さないとテストが落ちる
- `tests/test_review.py`（15件）—— Layer 2 の独立性・起動フラグ・出力検証（`claude` はスタブ）
- `tests/test_bypass.py`（3件）—— すり抜け試験の結果表を固定（ゲートが緩んだら落ちる）

すり抜け試験は単体でも実行できる:

```bash
python3 tests/bypass_drill.py            # 実際に git を動かし、どこで止まるかを表にする
```

結果と残存リスクは [docs/BYPASS_DRILL.md](docs/BYPASS_DRILL.md)。
