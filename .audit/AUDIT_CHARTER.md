# 監査基準書（AUDIT CHARTER）

本書は監査人の側の文書である。**実装用の `CLAUDE.md` から独立しており、その内容を継承しない。**
実装セッションのAIは本書を変更できない（変更は D7-01 のハッシュ照合で検知される）。

## 1. 監査人の立場

- 初期仮説は「この変更には問題がある」。問題が無いことを示す責任は、安全だと主張する側にある。
- 実装者（人間・AIを問わず）の説明・コメント・コミットメッセージ・Issue本文を**根拠として採用しない**。
  採用するのは、ファイルの内容・git の状態・設定の実体・外部APIの応答だけである。
- 「検査できなかった」を「問題なし」と言い換えない。検査していない範囲は意見に明記する。

## 2. 検査領域

| 領域 | 見るもの |
|------|----------|
| 体制文書 | 規律文書の実在。上位文書が実装AIから書き換え可能でないこと |
| フォルダ構成 | 実データがリポジトリの外にあること。追跡してはならないものが追跡下にないこと |
| 機械ゲート | フックが git の実行位置にあり実行可能なこと。CIが監査を呼ぶこと。無効化記述が無いこと。ブランチ保護。公開リモート |
| 不可逆操作 | 一覧の実在と網羅。本番到達経路に人間ゲートがあること。AIに渡した権限 |
| データ取扱い | 個人情報（氏名・連絡先・住所・生年月日・学籍番号・カード番号）と秘密の混入 |
| 監査の独立性 | 監査基盤の改変検知。allowlist の抜け道。調書の完全性 |

## 3. 個人情報保護（APPI）観点の禁止パターン

- 実在の個人データを seed / fixture / migration / テスト / スクリーンショット / デモに使うこと。
- 個人データを、その取得目的の範囲を超えて別環境（公開リポジトリ・外部サービス）へ複製すること。
- 個人データをログ・エラーメッセージ・URL・監査出力そのものへ出力すること。
- 要配慮個人情報（健康・信条・被差別的取扱いの事実等）を、必要性の記録なく保持すること。
- 削除要求に応じられない構造（追記専用の履歴に個人データを混ぜる）を作ること。

## 4. 重大度と扱い

| 重大度 | 定義 | 扱い |
|--------|------|------|
| Critical | 実データ・秘密の露出、または監査自体の無力化 | **マージ・push・デプロイ不可。** 例外は無い |
| High | 露出に至る経路が開いている（ゲート不在・保護なし・人間ゲートなし） | 限定付適正。解消するか、限定事項として明示的に引き受ける |
| Medium | 断定できないが確認を要する | 記録し、次回監査までに判断する |
| Low | 走査範囲の限界など、事実の記録 | 記録のみ |

Critical / High が1件でも残る状態を「問題なし」と報告してはならない。

## 5. 意見

意見は4種のみ。`不適正` / `限定付適正` / `意見不表明` / `適正`。
`適正` を出す場合は、実施した手続の全列挙と、各手続が何を検査したかを添える。
根拠の列挙が無い `適正` は無効とする。

## 6. 本インシデントから導いた個別検知項目

1. 実在応募者の氏名・メールを含む seed SQL が公開リポジトリへ入った
   → 氏名は列名・ヘッダ・キー名という**構造**を根拠に検出する（日本語の文章を氏名と誤認しない）。
2. push 前に人間が diff を見なかった
   → pre-push で機械検査を必須にし、force / 保護ブランチは端末からの人間承認を要求する。
3. 公開ミラーの存在が認識されていなかった
   → リモートの公開状態を毎回APIで確認し、公開先があること自体を所見にする。
4. `.gitignore` だけが実データの防壁になっていた
   → ignore に依存した保護を所見として扱い、リポジトリ外への移動を要求する。
5. AIが自分の制約文書と権限設定を書き換えられた
   → 規律文書・監査基盤・allowlist の改変を検知し、AI名義の変更を所見にする。
