## 残存リスク（止まらない経路）

- **#3 commit も push も --no-verify で飛ばす** … ローカルでは止まらない → CI（同じ検査で exit=1）
- **#4 フック本体を `exit 0` に書き換えて commit** … ローカルの commit は止まらない → 次の監査 D7-01 が改変を検知
- **#9b `git reset --hard` で監査基盤ごと巻き戻してから force push** … ローカルでは止まらない（フックが消えるため）→ 次の監査 D3-01/D7-01 が不在を検知

この 3 経路はいずれも「ローカルのフックを人間/AIが意図的に外す」ものである。
ローカルフックは対象リポジトリ内のファイルなので、原理的に外せる。
したがって最終防衛線は次の2つになる。

1. **CI**（`.github/workflows/audit.yml`）—— 外部からツールを取得して同じ検査を実行する。
   ローカルで何を外しても、push された内容に対して走る。
2. **ブランチ保護の必須チェック** —— CIの合格をマージの条件にする。
   これが無い場合、CIが落ちてもマージできるため、CIは通知にしかならない。

実測: `NEO-AX/YDB`（private・無料プラン）ではブランチ保護APIが 403 で使えない。
この状態では #3 の経路を機械的に塞げない。プランの変更、または公開ミラー側での
強制が必要である（D3-05 はこれを「検査不能」として意見に反映する）。
